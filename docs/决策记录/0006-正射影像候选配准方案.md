# 0006｜净山湖正射影像候选配准方案

日期：2026-09-27

## 决策背景

2023 正射影像已经提供了稳定的绝对位置，但公开 OSM 要素没有 Hole/ref 编号，逐洞公开表只有 Par 和距离。用户并不熟悉净山湖，因此让用户看航拍图后凭经验给 18 个对象编号，既不可解释也不能形成可复查证据。本轮采用“候选对象 + 可解释匹配 + 现场确认”的路线。

## 各类资料的职责

- **2023 正射影像**：提供覆盖范围、可视形状和像素叠加底图。GeoTIFF 的实际 CRS 是 EPSG:4548；运行时坐标统一转为 EPSG:4326/WGS84。影像不是高程数据，不能推出坡度。
- **公开逐洞资料**：提供 Hole 1-18 的洞号语义、Par、四档码数及长度等非地理特征。示意图只能帮助检查 Tee 端、Green 端、直洞/狗腿和障碍物相对关系，不能用图片像素直接反算经纬度。
- **OpenStreetMap/Overpass**：提供带 WGS84 坐标的未编号 Green、Tee、沙坑、水体、球车道等对象，用作绝对位置和空间关系 overlay。OSM 没有洞号关系，因此不单独产生洞级映射。

## 候选对象与评分

候选生成脚本 [`scripts/build_jingshanhu_spatial_candidates.py`](../../scripts/build_jingshanhu_spatial_candidates.py) 稳定生成空间对象 ID：Green `Gxx`、Tee `Txx`、Bunker `Bxx`、Water `Wxx`、Cartpath `Pxx`、Rough `Rxx`，以及 Tee→Green 直线长度比较 proxy `Cxx`。这些 ID 只代表空间对象，绝不代表 Hole 编号。

对每个 Hole 1-18，脚本保留一个 bestCandidate 和四个 alternatives，并记录长度、Par 宽范围、附近水体/沙坑、冲突和来源。分数上限为 0.68，只是便于排序的解释性分数，不是概率或验证置信度。相邻 Green→下一 Tee 转场距离只报告，不强制唯一编号或自动优化路线；因为没有独立洞号证据，18 洞当前均为 `candidate`，没有 `high-confidence-inferred` 或 `field-confirmed`。

`Cxx` 是两个对象质心的直线连接，明确标记为 proxy，不是球道 centerline。dogleg 的实际打球路线可能明显长于直线距离，长度只能做数量级交叉检查。

## 状态模型

- `unknown`：没有可信候选，不能进入可靠运行时洞号判断。
- `candidate`：有一个或多个可复查候选，但证据不足；允许在审查工作台中查看和标记待现场确认。
- `high-confidence-inferred`：多个独立证据一致、分析上高度可信，但尚未由现场或权威来源确认；本轮不自动生成。
- `field-confirmed`：只有真实下场、熟悉该球场人员、球场官方或足够权威资料明确确认后才能使用。用户在工作台点击候选不会改变为此状态。

第一次真实下场本身是验证流程：工具记录系统预测洞号、现场选择的实际洞号、时间、位置和确认来源。确认事件独立于自动候选状态，后续可据此人工复核和修正映射。

## 坐标链路与大文件策略

影像像素 → GeoTIFF affine → EPSG:4548 → pyproj → EPSG:4326/WGS84。预处理记录像元中心和半像元语义，测试四角、中心点和 round-trip。原始 ZIP、TIFF、解压目录、完整预览、tiles、cache 不进入 Git；只提交代码、metadata、轻量预览、测试和小型候选 JSON。

## 后续边界

本轮不制作精细 Polygon、DEM、坡度、GPS 轨迹、后端或正式地图产品。只有取得带明确洞号的独立控制点、现场采样或权威授权数据，才可把候选提升为高置信推断或现场确认，并进一步制作粗略洞 Polygon。
