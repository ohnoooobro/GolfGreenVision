# 0007｜首次现场测试模式

日期：2026-09-27

## 决策背景

Thread 03C/03D 已经生成净山湖的 Tee、Green 和 Hole mapping 候选，但这些候选仍没有独立的洞号证据，排序分也不是正确概率。Thread 04 的目标是第一次把手机带到球场，可靠记录真实位置和现场判断，为后续分析提供原始证据。因此现场模式优先保证数据可追溯和可恢复，不把候选推断包装成已验证结果。

## 1. 现场人员控制 `actualHole`

第一场测试由现场人员明确设置当前实际洞号。页面提供 Hole 1–18 selector、上一洞和下一洞；首次进入允许 `actualHole=null`，但在设置实际洞号前禁止保存 Tee/Green 样本。页面不会因为 GPS 移动或 `predictedHole` 自动切换 `actualHole`。

这样做是因为现场标牌、球场工作人员或熟悉球场者仍是当前最可靠的洞号来源。手动选择也能在候选错误时保护原始样本，避免系统自己跳到相邻错误球洞。

## 2. `predictedHole` 不覆盖 `actualHole`

`predictedHole` 表示系统根据当前候选数据给出的辅助判断，`actualHole` 表示现场测试人员当时确认的实际洞号。两者在样本、轨迹点和确认事件中分别保存，可以相等、不同或为空。

候选状态（`candidate`、`high-confidence-inferred` 等）和排序分也只作为证据上下文保存。排序分不是概率，不能单独把候选提升为 `field-confirmed`。只有后续人工复核或权威来源确认后，才允许更新候选数据；现场采样本身不静默改写 `course.geojson` 或 `spatial-candidates.json`。

## 3. Tee / Green 样本的真实含义

点击“到达发球台”或“到达果岭”各生成一个独立样本，不覆盖同一洞之前的样本。同一洞允许多次采样，以便处理误触、等待定位或重新测量。

每个样本至少包含：

- `sessionId`、`timestamp`、`sampleType`（`tee` 或 `green`）、`source=field`；
- `actualHole`；
- 当时的 `predictedHole`（可为空）和候选 mapping 信息（如存在）；
- WGS84 `latitude`、`longitude`、`accuracy`；
- 可用的 `altitude`、`heading`、`speed`。

Green 样本的语义必须写清：它是用户到达果岭区域时的位置，不代表旗杆位置、果岭几何中心或官方 Green Center。后续只能结合多个现场样本、正射影像和其他来源，另行推断 Green candidate。

`actualHole` 为空时禁止保存 Tee/Green；没有定位或精度较差时允许在提示后继续，样本必须保留当时真实的精度值或空值。

## 4. GPS accuracy 的记录方式

浏览器 `GeolocationPosition.coords.accuracy` 是水平精度估计值，单位为米。它不是球的位置精度，也不是测绘精度。样本和轨迹点原样保存该值，页面只使用阈值做操作提示：

- 无有效位置：`无定位`；
- `accuracy <= 10 m`：`良好`；
- `10 m < accuracy <= 25 m`：`一般`；
- `accuracy > 25 m`：`较差`。

这些分段不阻止采样，不对坐标作精度承诺。定位暂不可用时可以等待，也可以在明确提示后记录缺少坐标/精度的事件，不能用旧坐标冒充当前坐标。

## 5. Session 与浏览器本地持久化

点击“开始现场测试”时创建唯一 `sessionId`，并记录 `startTime`、`courseId=jingshanhu`、定位来源（`real` 或 `simulated`）、App/数据版本、候选数据版本、必要的非敏感设备/浏览器信息和可选备注。结束时写入 `endTime`、完成洞号和各类样本数量。导出 metadata 也保留定位来源，便于把桌面验收数据与真实 GPS 数据分开。

第一版使用浏览器本地存储，不建立账户、后端或云同步。Session、样本、确认事件和轨迹在每次变更后持久化；刷新、浏览器恢复或短暂中断后可恢复未完成 Session。恢复时沿用原 `sessionId`，不能新建 Session 覆盖未完成数据。

误触通过“撤销上一条采样”或本洞样本列表删除一条明确样本处理，删除不得清空整轮数据。删除后的数据应在导出中保持一致，必要时在备注或审计信息中说明。

## 6. 轻量 GPS track 策略

Session 运行时记录轻量轨迹，不把每次渲染或高频重复回调都写入存储：

1. 第一个有效定位回调立即记录；
2. 后续仅在距上个 track point 至少 10 秒或移动至少 10 米时记录；
3. 每个点保存 `timestamp`、WGS84 经纬度、`accuracy`、当时的 `actualHole` 和 `predictedHole`；
4. `actualHole` 为空时仍可记录轨迹点，但点中保留空值，不猜测洞号；
5. 轨迹只属于当前 Session，不能阻塞 Tee、Green、确认事件和导出。

该策略足以保留转场和现场路线的数量级信息，同时控制手机存储和导出体积。若设备定位回调过少，优先保证事件样本和确认事件完整。

## 7. 导出与隐私边界

结束 Session 后由用户下载 JSON，顶层结构包含：

```json
{
  "session": {},
  "samples": [],
  "confirmationEvents": [],
  "track": [],
  "metadata": {}
}
```

`track` 在实现未启用时可以为空数组，但不能把轨迹混入 `samples`。导出文件通过项目 schema/validator 检查后交给 Thread 05。原始导出文件不应手工覆盖或删除字段；分析结果应另存为派生数据。

真实 GPS 坐标属于私人测试数据，默认只保存在用户指定的私有目录（例如 `field-tests/private/`）或下载目录，不进入 Git。测试 fixture 使用模拟坐标，并保留模拟标记，不能与真实 `source=field` 数据混合。

## 8. 进入 Thread 05 的方式

Thread 05 接收一轮未经篡改的导出 JSON、候选数据版本、设备/浏览器信息和现场备注，重点分析：

- 实际洞号与系统预测的对应关系；
- Tee/Green 多次样本的空间分布和 GPS accuracy；
- 轨迹中的转场方向和相邻洞关系；
- 正确、错误和 `uncertain` 的确认事件；
- 低精度、无定位、刷新恢复和误触删除等数据质量问题。

Thread 05 再根据多来源证据决定是否更新候选状态或生成派生 mapping。Thread 04 只负责采集和导出，不自动可靠切洞、不制作正式球场地图、不把 Green 到达点当成官方中心，也不进入后端、登录、云同步或记分功能。
